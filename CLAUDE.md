# Mai — Project Notes for Claude

## What this project is

Mai is a Paper plugin for Minecraft 26.2 (Mojang's year-based versioning; it follows 1.21.11) that spawns humanoid NPCs (Mannequins — `EntityType.MANNEQUIN`, the dedicated vanilla mob added in 1.21) and drives them with code. The long-term goal is to ship **Redstone** (formerly called MaiBench; use "Redstone" from now on): a public benchmark that pits AI agents against each other inside Minecraft and scores them on the milestones they unlock (mine wood, craft tools, kill dragon, etc.). The author plans to write a research paper on the results.

Today the plugin is the substrate the benchmark will run on. A brain (LLM-driven decision loop) will be plugged into the `HumanoidActionAgent` later — but **only once the body is reliable**. Movement bugs are gating everything.

## What's in the repo

- `src/main/java/me/advait/mai/`
    - `Mai.java` — plugin entry. Wires up `Catalog`, `Settings`, `PatheticAgent`, listeners, ACF commands.
    - `Catalog.java` — registry of all spawned `Humanoid`s. `register(name, location)` spawns. `unregister(humanoid)` despawns.
    - `body/Humanoid.java` — the NPC wrapper. Owns the Mannequin entity, equipment, inventory, action agent.
    - `command/HumanoidCommand.java` — `/h …` ACF subcommands. Instructions (come, follow, guard, attack, mine, place, give/take, goto, ...) are thin wrappers over `assistant.Tools`; the target humanoid is an explicit name, else the sender's `/h select`, else the nearest one. Management (spawn/list/delete/rename) and `debug particles|pathcheck|queue|watch` live here too.
    - `assistant/` — the assistant layer (see "Assistant" below): `Assistant` (per-humanoid will: one behavior or one action queue), behaviors (`FollowBehavior`, `GuardBehavior`, `CombatBehavior`), `Tools` (the tool registry), `Observation` (JSON state), `ChatIntents` + `AssistantChatListener` (talk to it in chat), `Motor` (direct vanilla-legal steering), `Navigator` (retargetable pathfinding legs), `Duel` (PvP benchmark).
    - `brain/action/` — action queue framework. `HumanoidActionAgent.addActions(...)` returns a `CompletableFuture<ActionResult>`. Actions = `HumanoidWalkToAction`, `HumanoidMineAction`, `HumanoidBuildAction`.
    - `pathetic/` — Baritone-inspired pathfinder + locomotion. **Recently rewritten — do not redesign without reading the existing types.**
        - `PatheticAgent.java` — `getAnnotatedPath(humanoid, from, to)` returns a `CompletableFuture<Optional<AnnotatedPath>>`.
        - `movement/` — `MovementType` sealed interface, `MovementRegistry`, `MovementExecutors` (shared physics primitives), `TickContext`, `AirControl` (predictive airborne controller + takeoff planner; see "Movement physics" below).
        - `movement/types/` — locomotion: `WalkFlat`, `WalkDiagonal`, `StepUp`, `StepDown`, `FallSafe`, `FallUnsafe`, `SprintJump`, `LadderClimb`, `Swim`. World-editing (Baritone-style): `MineThrough`/`MineStepUp` (break blocks to tunnel through/up), `BridgePlace`/`PillarUp` (place blocks to bridge gaps / pillar up). Editing moves are gated on `HumanoidCapabilities.canMine`/`canBridge` (derived from inventory) and registered last so free locomotion always wins on cost ties. See "Block editing in the pathfinder" below.
        - `path/AnnotatedPath.java` — `simplify()` drops collinear waypoints. Don't re-classify across simplified spans — caused an infinite replan loop once. Mine/bridge moves use `Locomotion.MINE`/`BRIDGE` execution hints precisely so simplify keeps them per-cell (collapsing them strands the bot in a gap).
        - `debug/PathDebugLog.java` — console output gated by `HumanoidWalkToRunnable.isDebugMode()` (toggle with `/h debug particles` or console `/mai debug on|off`). Independently, an optional sink receives every event; the obstacle harness attaches one per run so each per-run log contains the full decision trace.
        - `processor/SearchCache.java` — per-request material cache and one-entry classification cache shared by the cost and validation processors.
        - `config/MovementTuning.java` — runtime tuning API over `movement:` (see "Tuning" below).
- `mc-server/` — local dev server. `deploy.sh` builds, copies the jar, kills `server.jar` (carefully — see [[feedback_kill_caution]]), and restarts under `screen -dmS mc`. Note: the WSL dev box has `tmux` but not `screen`.
- `src/main/resources/settings.yml` — all tunable movement constants under `movement:`, plus `movement_profiles:`. Don't hardcode physics — pipe through `MovementConfig`. On load, `YMLBase` merges any keys missing from the on-disk file from the bundled resource, so new keys reach old installs.
- `tools/gen_obstacles.py` — fixture generator. `tools/obstacle_report.py` — per-fixture pass-rate table across one or more logs (exit 1 below `--min-rate`; use it to separate broken from flaky).

## Obstacle test harness (`me.advait.mai.obstacle`)

A deterministic, headless parkour/terrain test harness for verifying movement correctness. **This is plain Mai functionality — no LLM involved.** (Redstone, the AI-agent benchmark, is a separate future repo.) It is the user's primary regression tool: build a small arena from a text file, spawn a humanoid, walk it to the goal, watch every tick, print a machine-parseable result, then tear down leaving no trace.

- **Files**: `ObstacleParser` → `ObstacleFile` (header + grid), `ArenaBuilder` (build/teardown, chunk pinning, snapshot invalidation), `ObstacleTester` (orchestration: run/batch/cancel/list/reload/tp, all `CommandSender`-safe), `ObstacleCommand` (ACF `/mai`), `ObstacleLog` (per-run debug log), `Result`.
- **Commands** (top-level `/mai`, separate from `/h` so the **console** can drive it without a `Player`): `mai test run <stem>`, `mai test all`, `mai test list`, `mai test cancel`, `mai test reload`, `mai test tp <stem>` (in-game only), `mai debug [on|off]`, `mai reload` (hot-reload settings.yml), `mai tune list|get|set|profile|save`, `mai do <humanoid> <tool> [json]`, `mai tools` (schema JSON), `mai observe <humanoid>`, `mai spawn <name> <x> <y> <z> [world]`, `mai give <humanoid> <item> [count]` (admin setup), `mai duel [rounds] [styleA] [styleB] [weapon]`, `mai duel trace` (per-tick `[Combat]` decision log), `mai ask <humanoid> <message>` (Claude chat brain). Permission: **`mai.obstacle.run`** (console always has it; in-game defaults to op).
- **Per-run logs** contain, per tick, position, velocity (`vx vy vz hspeed`) and ground flag, interleaved with every PathDebug event stamped `[tick]`. Velocity read at the start of a tick plus that tick's input equals the tick's displacement, so the logs double as physics calibration data.
- **Result contract** (grep `[Obstacle] RESULT`): `[Obstacle] RESULT name=<stem> status=<PASS|FAIL|TIMEOUT|ERROR> ticks=<n> reason=<reason> humanoid=<uuid>`. Batch ends with `[Obstacle] BATCH passed=… failed=… timeout=… error=… total=… elapsed_ms=…`.
- **`.obstacle` format**: header (`key: value`) + `---` + whitespace grid. Rows north→south, cols west→east. Cells: integer N = N blocks on floor, `.` = floor only, `_` = void (no floor, fall-through), `S`/`E` = start/end (optional digit suffix = pillar height, e.g. `E4`). Exactly one `S` and one `E`. `#` lines are comments. Max 32×32. Optional `expect: no_path` marks a course that is impossible under vanilla physics; it PASSes (`reason=refused_impossible`) only if the planner refuses it, and FAILs if the bot tries. Optional `blocks: a=oak_slab d=oak_door[facing=east] ...` defines lowercase legend letters (not s/e) for real block types; a cell token is optional digits (blocks of `material`) then an optional letter (one more block of that type on top), e.g. `a`, `2a`, `Sa`, `E1u`. Doors place both halves. Optional header keys for editing tests: `bot_tool: <Material>` (e.g. a pickaxe — without it `canMine` is false), `bot_blocks: <Material> [count]` (stock for bridging/pillaring), `ceiling: <N>` (solid roof at `originY+N` over floored cells, encloses the course into a tunnel so mine-*through* is forced over climb-over). The suite is ~161 fixtures spanning walks (flat/vertical/diagonal), staircases (up/down to height 10, pyramids, valley), gaps & sprint-jumps, pillar-jumps, corners/mazes, mining (wall thickness, tool tiers, materials, long tunnels), bridging (gap width, block materials, double gaps), pillar-up, ledge drops (safe and damaging, cardinal and diagonal), ascending/descending gap jumps, tight single-cell landings, mixed-width gap chains, real terrain (`terrain-*`: slabs, paths, carpet, soul sand, ice, fences, gates, doors, stairs), and impossible courses the planner must refuse — most generated by `tools/gen_obstacles.py` (rerun it to regenerate; it never overwrites the hand-curated seeds and `terrain-*`). On enable the plugin copies every bundled fixture missing from `mc-server/plugins/Mai/obstacles/` (never overwriting local edits); run `mai test reload` after dropping files in by hand.
- **Arena world**: `settings.yml` → `obstacle.world` (`name`, `type` = `VOID`/`FLAT`/`NORMAL`, `auto_create`). On enable, an already-loaded world of that name is used as-is; otherwise a dedicated world is created/loaded with the chosen generator (`VoidGenerator` for VOID). Default is a dedicated `obstacles` VOID world. Point `name` at `world` to build in the overworld instead. Horizontal origin is `obstacle.arena_origin` (x/z, default 0/0); floor Y is per-file `origin_y` (default 120). Per-run logs land in `mc-server/plugins/Mai/obstacle-logs/`.
- **Two non-obvious correctness notes** (don't regress these):
  - Pathetic caches chunk snapshots in a **static, never-auto-refreshed** map (`FailingNavigationPointProvider.SNAPSHOTS_MAP`). The harness rewrites the same chunks every run, so `ArenaBuilder` calls `FailingNavigationPointProvider.invalidateChunk(...)` after build/teardown — otherwise pathfinding sees the previous arena and returns `no_path`.
  - The arena sits far from spawn; its chunks are pinned with plugin chunk tickets (kept for the plugin lifetime) so the humanoid ticks instead of going invalid (which reads as `died`). The batch waits `SETTLE_TICKS` before each run so a prior run's in-flight async pathfind can't re-cache a stale snapshot.

## Movement physics (read before touching jumps or falls)

- **Vanilla-legitimate physics only.** The body must never move faster than a player could; otherwise benchmark results are meaningless and any anticheat flags it. A sprint-jump's takeoff speed is capped at current ground speed plus `sprint_jump_boost`. An older version passed long pillar jumps by injecting extra velocity; that is gone on purpose. Courses that need it are `expect: no_path` fixtures now.
- **Measured model** (confirmed from per-run logs): displacement this tick = velocity read at tick start + our input. Then horizontal velocity is multiplied by `air_drag` (0.91) in air, or by `slipperiness * air_drag` (about 0.546) on the ground, including the takeoff tick. Vertical: `vy = (vy - gravity) * vertical_drag`.
- **`AirControl.steer`** simulates the remaining airtime and picks this tick's input (clamped to the vanilla air-accel budget) so the predicted touchdown is the landing block's center, braking as needed. Used by sprint-jump and both fall types. Don't go back to "push toward the waypoint every tick": it saturates at the drag equilibrium (about 0.29 b/t) and overshoots every short or tight landing.
- **`AirControl.takeoffSpeeds`** returns the preferred and minimum takeoff speed for a jump. The executor jumps at the lip if the minimum is reachable, otherwise it retreats for a run-up (or force-jumps if there is no room behind).
- **Planner run-up check**: `SprintJump.matches` counts standable blocks behind the takeoff block, simulates sprint acceleration from a standstill over that run, and rejects jumps that speed can't make. It uses the same takeoff geometry as the executor (center about 0.35 + one tick's travel behind the lip). Keep planner and executor geometry in sync.
- **Sprint-jump cost** = `walk_flat * distance + sprint_jump_base + gap * sprint_jump_per_gap + ...`. It must never be cheaper per block than walking, or A* plans the longest jump that fits, including "jumps" over flat ground.
- `SprintJump.matches` also requires at least one floorless intermediate column (a real gap).
- `FallSafe`/`FallUnsafe` check the **landing** column from source height down (plus the corner columns for diagonal drops). Standing on the landing is success regardless of phase.
- The driver chains into the next waypoint in the same tick when one completes, so no tick goes without a decision. `groundAccelerate` is idempotent per tick (`TickContext.accelTick`) so chaining never double-accelerates.
- Arrival requires being on the ground; passing over the target column mid-jump is not arriving.
- **Run-jumping** (`navigation.sprint_jump_flat`): on a straight flat segment at sprint speed with the waypoint at least `sprint_jump_flat_min_distance` (5) away, `WalkFlat` sprint-jumps (`RUN_JUMP` event), which is how players outrun plain sprinting. `MovementExecutors.flatRunJumpClear` requires a level full-height floor (no slow blocks) and 3 blocks of headroom along the whole ~4.5-block arc, so it never jumps into a turn, a ceiling or a step.
- Pathfinding takes about 50-100 ms per request on this server. The search itself is fast; the time is Pathetic's async handoff plus one main-thread tick for annotation.

## Real terrain (partial and special blocks)

The planner only sees `Material`s, so the executor reads real collision shapes where it matters. Don't regress these:
- `PatheticAgent.feetCell` maps an entity standing on a partial block (slab, dirt path, farmland, soul sand, carpet, chest) to the cell above it. Without it, start and target cells sit inside the floor block and every walk to a player on a path block fails.
- `MovementExecutors.collisionTop` uses the block's collision shape, not `getBoundingBox()` (a fence's outline is 1.0, its collision 1.5). `stepRise`/`needsJumpUp` skip the jump for rises within the vanilla 0.6 step height (slabs, paths, carpet), and StepUp completes when the feet are on the real top. `obstacleAheadNeedsJump` only hops rises in (0.6, 1.25].
- `BlockClassifier`: lava, fire, soul fire and wither roses are never traversable; `Swim` is water-only. Fences, walls and gates are `isTall` (1.5): never a floor, so never a step. Wooden doors and fence gates are `isOpenable`: passable to the planner, and the driver opens them (`openDoorsAhead`). Iron doors stay solid.
- `SprintJump` never takes off from a slow block (soul sand, honey): the takeoff model assumes full sprint speed.
- `slipperinessBelow` samples 0.5 below the feet like vanilla, so it reads a slab or path itself rather than the block under it.
- Terrain fixtures are `terrain-*` (slabs, paths, carpet, soul sand, ice, fences, gates, doors, iron door, stairs, a mixed village street).

## Assistant (commands, chat, and the future LLM interface)

- **One entry point.** Every capability is a named tool in `assistant.Tools` with typed params (`status, come, goto, follow, guard, attack, stop, mine, place, look_at, jump, say, inventory, equip, give, teleport_to`). `/h` commands, chat and `/mai do` all call `Tools.run(name, humanoid, jsonArgs, requester)`, which returns a `CompletableFuture<String>` (immediate for behaviors, on completion for queued work; failures are `ToolException` messages for the user). `Tools.schema()` renders JSON-schema function definitions and `Observation.of(h)` the matching state, so an LLM loop is: observe, pick a tool, run it. Add new abilities as tools, not as bespoke commands.
- **One job at a time.** `Assistant.of(h)` holds either a `Behavior` (ticked every tick by a shared ticker) or the action queue; `setBehavior`/`run`/`stopAll` cancel the other. Don't drive actions or behaviors around it.
- **Moving targets.** `HumanoidWalkToRunnable` has an `arrivalRadius` and `retarget(Location)`; a retarget replans only when the current movement is safe to cancel. `Navigator` wraps this for behaviors (one live walk, retarget only after the goal moves 2+ blocks, 1 s back-off after a failure). `FollowBehavior.landingSpot` resolves a jumping/flying target to the standable cell below it.
- **Combat** (`CombatBehavior`, vanilla rules only): pathfind when far or out of sight, else step directly with `Motor` (same accel budget as the path executor). Swings only within 3.0 reach (eyes to hitbox) at the weapon's attack-speed cooldown with vanilla charge scaling (`0.2 + 0.8c²`); crits by jumping and swinging while falling without sprint (x1.5); sprint hits add the vanilla extra knockback and slow the attacker, then release sprint 2 ticks (w-tap); strafes and never steps off a ledge. `ItemUtil` reads the effective attribute-modifier component (item defaults included). Style `BASIC` is the naive baseline for duels.
- **Duel benchmark** (`mai duel`): two humanoids on a platform at x=400 in the obstacle world; prints `[Duel] RESULT`/`SERIES`. It is only fair because sides swap every round, spawn order alternates every two rounds (the server ticks entities in spawn order, and moving first means swinging first: basic-vs-basic was 15-5 before), and the assistant ticker shuffles behavior order each tick. Check `mai duel 40 basic basic` stays near 20-20 after touching it. Findings so far (40 rounds each vs BASIC, iron sword): w-tap 23-17, recharge-only crits 21-19, both 23-17 (noise-level); strafing 17-23 (no aim to dodge, slower approach); approach crits 0-40 (airborne you're hit first and knocked further); `space_out` (back out of reach while recharging) 19-21. Why everything is noise vs BASIC: per-round stats show both sides land 3-4 full-charge sprint hits (6 each), sprint knockback separates them after every hit so neither ever recharges inside reach (no crits happen), and each re-entry is a symmetric full-charge trade won by whoever acts first that tick. Beating a perfect-aim rusher on flat ground needs a real reach or timing asymmetry, not footwork tweaks. Hence the defaults: crits on (recharge hops only), `approach_crits` and `strafe` off. Reach is symmetric on the ground, so full-charge trades are coin flips; an airborne fighter's eyes are above the target, which lengthens its own reach to the target.
- **Chat**: "<Name>, follow me", "@Mai mine this", "mai attack nearest". `ChatIntents` is keyword rules returning (tool, args). Permission `mai.humanoid.command` (op by default).
- **Claude chat brain** (`LlmBrain`, off by default): with `assistant.llm.enabled: true` and a key (`assistant.llm.api_key` or `ANTHROPIC_API_KEY`), chat goes to Claude (official `anthropic-java` SDK, loaded by Paper from plugin.yml `libraries:`, so it is `provided` in the pom). Each message is a fresh request: system prompt + the last 8 chat lines + `Observation` JSON + the message, with every tool except `say` (plain text is spoken). Tool calls run on the server thread; one-shot jobs are awaited up to `tool_wait_seconds`, then reported as still running. Any API failure falls back to `ChatIntents`. Console: `mai ask <humanoid> <message>`.
- Tunables live in `settings.yml -> assistant:` (follow distance/teleport distance, combat reach/range/crits/strafe/w_tap/min_charge, guard radius), read live.

## Tuning (for humans now, models later)

`MovementTuning` exposes every leaf under `movement:` as a key such as `costs.walk_flat` or `navigation.stuck_replan_ticks`. `snapshot()`, `get`, and `set` validate the key and type, then rebuild `MovementConfig` and the registry immediately. `applyProfile(name)` applies `movement_profiles.<name>` (shipped: `default`, `safe`, `speedrun`; write profiles as nested YAML, not dotted keys). `save()` persists. In-flight walks keep their config; new walks use the new one. The driver's replan and stuck thresholds are config too (`navigation.lookahead_depth`, `periodic_replan_ticks`, `emergency_jump_ticks`, `stuck_replan_ticks`). Console: `mai tune ...`.

## Block editing in the pathfinder (mining & placing)

The pathfinder treats the world as **mutable**: it will break or place blocks as part of an A* route, and re-paths when the world changes. Do not "fix" this by stripping the editing moves — it's intentional.

- **Moves**: `MineThrough`/`MineStepUp` break the breakable block(s) in the way then walk/step in; `BridgePlace` places a support under the next cell across a gap; `PillarUp` jumps and places a block under the feet. Each `matches()` only fires on cells the natural moves reject (blocked-but-breakable, or floorless gap), so they never shadow free locomotion.
- **Execution reuses existing actuators**: mining drives `MannequinBlockBreaker` (multi-tick; the in-flight future lives on `TickContext.subAction`, reset by the driver on every waypoint advance/replan); placing drives `HumanoidBuildAction.placeBlock` (requires a solid neighbour to build against; decrements + writes the held stack back to the hand).
- **Mining/placing visuals**: both call `entity.swingMainHand()`; mining additionally broadcasts the vanilla block-cracking overlay each tick via `Player.sendBlockDamage(loc, progress, mannequin)` to players within 64 blocks, throttled to destroy-stage changes and cleared (progress 0) on cancel — a successful break clears it client-side on its own. Caveat: the swing animation may not render on a `Mannequin` (it is a display-oriented entity; `swingMainHand` already reaches the NMS swing broadcast with no `Mob` guard, so non-rendering is a client-side limitation, not something the server can fix). The crack overlay renders regardless since it is attached to the block. No-op when no players are nearby (e.g. the headless obstacle world).
- **Cost model** (all in ticks, summed with the existing costs): mining = `hardness * divisor / toolSpeed + durabilityPenalty` (`divisor` 30 with the right tool / 100 without); placing = `place_block_cost + equip_cost + value_weight * placementValue(block) / log2(count+2)`. Scarcity means the bot bridges with cobblestone (value 1, abundant), never a diamond block (value 4000) unless that's all it has. Unbreakable/protected blocks and "no block to place" cost `cost_inf` (never chosen). Constants live in `settings.yml` → `movement.{mine,place}` and `movement.pathfinding.{mining_enabled,bridge_enabled}`; `HumanoidCapabilities.from()` pre-extracts thread-safe tool/placement numbers on the main thread for the async cost processor.
- **Adaptivity**: `BlockClassifier` gained `isBreakable`/`hardness`/`placementValue`. `WorldChangeListener` (block break/place/burn/fade/decay/explode events) invalidates the pathfinder's static snapshot cache (`FailingNavigationPointProvider.invalidateChunk`) and flags nearby in-flight `HumanoidWalkToRunnable`s (`onWorldChange` → `worldDirty`) to replan immediately. The bot's own edits bypass Bukkit events, so `MannequinBlockBreaker` and `HumanoidBuildAction.placeBlock` invalidate the snapshot directly. `worldDirty` is a 4th replan trigger in the runnable alongside pathNull/lookahead/periodic.

## Conventions

- **Commit messages**: short single-sentence subject only, no body, no Claude footer. See [[feedback_commit_style]].
- **Pathfinding correctness**: when in doubt, surface a `PathDebugLog.event(...)` line. The debug log is the user's primary way to diagnose stuck bots.
- **Never snap the target to the ground** — long-term the bot needs to bridge to elevated targets. Resolve block-coord ambiguity (e.g. edge-standing players) by checking AABB corners, not by moving the target.
- **Physics constants** live in `settings.yml` → loaded into `MovementConfig`. Don't sprinkle magic numbers into movement types.
- **Console-safe APIs**: anything the harness or future CI needs must take `CommandSender`, not `Player`. Use `Bukkit.getWorlds().getFirst()` (or a configured arena world) when no player context exists.
