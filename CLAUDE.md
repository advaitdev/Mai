# Mai — Project Notes for Claude

## What this project is

Mai is a Paper plugin for Minecraft 26.2 (Mojang's year-based versioning; it follows 1.21.11) that spawns humanoid NPCs (server-side fake players by default, or Mannequins — `EntityType.MANNEQUIN`; see "Bodies") and drives them with code. The long-term goal is to ship **Redstone** (formerly called MaiBench; use "Redstone" from now on): a public benchmark that pits AI agents against each other inside Minecraft and scores them on the milestones they unlock (mine wood, craft tools, kill dragon, etc.). The author plans to write a research paper on the results.

Today the plugin is the substrate the benchmark will run on. A brain (LLM-driven decision loop) will be plugged into the `HumanoidActionAgent` later — but **only once the body is reliable**. Movement bugs are gating everything.

## What's in the repo

- `src/main/java/me/advait/mai/`
    - `Mai.java` — plugin entry. Wires up `Catalog`, `Settings`, `PatheticAgent`, listeners, ACF commands.
    - `Catalog.java` — registry of all spawned `Humanoid`s. `register(name, location)` spawns. `unregister(humanoid)` despawns.
    - `body/Humanoid.java` — the NPC wrapper. Owns the body (a fake player by default, or a Mannequin; see "Bodies"), equipment, inventory, action agent.
    - `body/fake/` — `FakePlayer` (a `ServerPlayer` the server simulates), `FakeConnection` (an open connection that drops every packet), `FakePlayers` (spawn/remove/`isFake`).
    - `body/Body.java` — the humanoid's keyboard and mouse, and the **only** thing that moves it (see "Movement physics"). `BodyListener` releases all keys at each tick start.
    - `body/Hands.java` — the humanoid's right click under a player's rules: every block placement and bucket use (see "Hands").
    - `body/Reflexes.java` — survival reflexes for unplanned falls: chain/block clutch and water-bucket clutch (see "Clutching").
    - `command/HumanoidCommand.java` — `/h …` ACF subcommands. Instructions (come, follow, guard, attack, mine, place, give/take, goto, ...) are thin wrappers over `assistant.Tools`; the target humanoid is an explicit name, else the sender's `/h select`, else the nearest one. Management (spawn/list/delete/rename) and `debug particles|pathcheck|queue|watch` live here too.
    - `assistant/` — the assistant layer (see "Assistant" below): `Assistant` (per-humanoid will: one behavior or one action queue), behaviors (`FollowBehavior`, `GuardBehavior`, `CombatBehavior`), `Tools` (the tool registry), `Observation` (JSON state), `ChatIntents` + `AssistantChatListener` (talk to it in chat), `Motor` (direct steering through `Body` keys), `Navigator` (retargetable pathfinding legs), `Duel` (PvP benchmark).
    - `brain/action/` — action queue framework. `HumanoidActionAgent.addActions(...)` returns a `CompletableFuture<ActionResult>`. Actions = `HumanoidWalkToAction`, `HumanoidMineAction`, `HumanoidBuildAction`.
    - `pathetic/` — Baritone-inspired pathfinder + locomotion. **Recently rewritten — do not redesign without reading the existing types.**
        - `PatheticAgent.java` — `getAnnotatedPath(humanoid, from, to)` returns a `CompletableFuture<Optional<AnnotatedPath>>`.
        - `movement/` — `MovementType` interface, `MovementRegistry`, `MovementExecutors` (key-press helpers and geometry probes), `TickContext`, `AirControl` (predictive airborne controller + takeoff planner; see "Movement physics" below).
        - `movement/types/` — locomotion: `WalkFlat`, `WalkDiagonal`, `StepUp`, `StepDown`, `FallSafe`, `FallUnsafe`, `SprintJump` (any direction, see "Parkour"), `LadderClimb`, `Swim`, `FallIntoWater` (any height into water), `WaterClutch` (bucket MLG, see "Clutching"). World-editing (Baritone-style): `MineThrough`/`MineStepUp` (break blocks to tunnel through/up), `BridgePlace`/`PillarUp` (place blocks to bridge gaps / pillar up). Editing moves are gated on `HumanoidCapabilities.canMine`/`canBridge` (derived from inventory) and registered last so free locomotion always wins on cost ties. See "Block editing in the pathfinder" below.
        - `path/AnnotatedPath.java` — `simplify()` drops collinear waypoints. Don't re-classify across simplified spans — caused an infinite replan loop once. Mine/bridge moves use `Locomotion.MINE`/`BRIDGE` execution hints precisely so simplify keeps them per-cell (collapsing them strands the bot in a gap).
        - `debug/PathDebugLog.java` — console output gated by `HumanoidWalkToRunnable.isDebugMode()` (toggle with `/h debug particles` or console `/mai debug on|off`). Independently, an optional sink receives every event; the obstacle harness attaches one per run so each per-run log contains the full decision trace.
        - `processor/SearchCache.java` — per-request material cache and one-entry classification cache shared by the cost and validation processors.
        - `config/MovementTuning.java` — runtime tuning API over `movement:` (see "Tuning" below).
- `mc-server/` — local dev server (26.2). `deploy.sh` builds, copies the jar, kills `server.jar` (carefully — see [[feedback_kill_caution]]), and restarts it in a `screen` or `tmux` session named `mc`.
- `mc-server-26.3/` — a second, gitignored Paper 26.3 (build 257) test server on port 25566 (tmux session `mc263`), so movement is checked on both versions without upgrading the 26.2 worlds.
- `src/main/resources/settings.yml` — all tunable movement constants under `movement:`, plus `movement_profiles:`. Don't hardcode physics — pipe through `MovementConfig`. On load, `YMLBase` merges any keys missing from the on-disk file from the bundled resource, so new keys reach old installs.
- `tools/gen_obstacles.py` — fixture generator. `tools/obstacle_report.py` — per-fixture pass-rate table across one or more logs (exit 1 below `--min-rate`; use it to separate broken from flaky).

## Obstacle test harness (`me.advait.mai.obstacle`)

A deterministic, headless parkour/terrain test harness for verifying movement correctness. **This is plain Mai functionality — no LLM involved.** (Redstone, the AI-agent benchmark, is a separate future repo.) It is the user's primary regression tool: build a small arena from a text file, spawn a humanoid, walk it to the goal, watch every tick, print a machine-parseable result, then tear down leaving no trace.

- **Files**: `ObstacleParser` → `ObstacleFile` (header + grid), `ArenaBuilder` (build/teardown, chunk pinning, snapshot invalidation), `ObstacleTester` (orchestration: run/batch/cancel/list/reload/tp, all `CommandSender`-safe), `ObstacleCommand` (ACF `/mai`), `ObstacleLog` (per-run debug log), `Result`.
- **Commands** (top-level `/mai`, separate from `/h` so the **console** can drive it without a `Player`): `mai test run <stem>`, `mai test all`, `mai test list`, `mai test cancel`, `mai test reload`, `mai test tp <stem>` (in-game only), `mai debug [on|off]`, `mai reload` (hot-reload settings.yml), `mai tune list|get|set|profile|save`, `mai do <humanoid> <tool> [json]`, `mai tools` (schema JSON), `mai observe <humanoid>`, `mai spawn <name> <x> <y> <z> [world]`, `mai give <humanoid> <item> [count]` (admin setup), `mai duel [rounds] [styleA] [styleB] [weapon]`, `mai duel trace` (per-tick `[Combat]` decision log), `mai ask <humanoid> <message>` (Claude chat brain). Permission: **`mai.obstacle.run`** (console always has it; in-game defaults to op).
- **Per-run logs** contain, per tick, position, velocity (`vx vy vz hspeed`), ground flag, the keys and view the body ticked with (`keys=W+jump+sprint yaw=… pitch=…`) health (`hp=`) and wall contact (`hc=-|minor|hard`, the last move's vanilla horizontal collision; `hard` ends a sprint), interleaved with every PathDebug event stamped `[tick]`. Velocity read at the start of a tick plus that tick's input equals the tick's displacement, so the logs double as physics calibration data.
- **Chase benchmark** (`mai test chase <stem> [lead]`, `mai test chaseall [lead]`): a Runner walks the course; `lead` ticks after its first step a Hunter spawns at the start and chases it with the real attack behavior (`CombatBehavior`), caught once in swing reach. `[Obstacle] CHASE name=… status=CAUGHT|LOST ticks=… runner_arrived=… excess=…`, where `excess` is how many ticks later than a perfect chaser (the Runner's own time, `lead` behind) it got there. Last run (lead 40, player bodies): 194/194 caught, total excess 9 ticks. A lost chase says why: `runner_died`, `runner_gone` or `runner_fell` (the Runner sliding off the goal after arriving is how the stopping bugs under "Run-jumping" were found). With `mai debug on` it logs a per-tick `[Chase]` trace of both bots.
- **Result contract** (grep `[Obstacle] RESULT`): `[Obstacle] RESULT name=<stem> status=<PASS|FAIL|TIMEOUT|ERROR> ticks=<n> reason=<reason> humanoid=<uuid>`. Batch ends with `[Obstacle] BATCH passed=… failed=… timeout=… error=… total=… elapsed_ms=…`.
- **`.obstacle` format**: header (`key: value`) + `---` + whitespace grid. Rows north→south, cols west→east. Cells: integer N = N blocks on floor, `.` = floor only, `_` = void (no floor, fall-through), `S`/`E` = start/end (optional digit suffix = pillar height, e.g. `E4`). Exactly one `S` and one `E`. `#` lines are comments. Max 64×64. Optional `expect: no_path` marks a course that is impossible under vanilla physics; it PASSes (`reason=refused_impossible`) only if the planner refuses it, and FAILs if the bot tries. Optional `blocks: a=oak_slab d=oak_door[facing=east] ...` defines lowercase legend letters (not s/e) for real block types; a cell token is optional digits (blocks of `material`) then an optional letter (one more block of that type on top), e.g. `a`, `2a`, `Sa`, `E1u`; `N*x` is N blocks of legend `x` and `2+3*w` two blocks then three `w` (ponds: `blocks: w=water`, placed without physics so it doesn't flow). Doors place both halves. `place: col,height,row=block ...` (repeatable) puts single blocks anywhere in 3D (height 1 = first block above the floor): floating platforms, head-hitters, ladders, canopies. `bot_items: water_bucket cobblestone:64` stocks extra items. `knockback: <tick> <vx> <vy> <vz>` shoves the bot at that tick, like a hit (tests the reflexes). Optional header keys for editing tests: `bot_tool: <Material>` (e.g. a pickaxe — without it `canMine` is false), `bot_blocks: <Material> [count]` (stock for bridging/pillaring), `ceiling: <N>` (solid roof at `originY+N` over floored cells, encloses the course into a tunnel so mine-*through* is forced over climb-over). The suite is 203 fixtures spanning walks (flat/vertical/diagonal), staircases (up/down to height 10, pyramids, valley), gaps & sprint-jumps, pillar-jumps, corners/mazes, mining (wall thickness, tool tiers, materials, long tunnels), bridging (gap width, block materials, double gaps), pillar-up, ledge drops (safe and damaging, cardinal and diagonal), ascending/descending gap jumps, tight single-cell landings, mixed-width gap chains, real terrain (`terrain-*`: slabs, paths, carpet, soul sand, ice, fences, gates, doors, stairs), angled parkour (`pk-*`), tree canopies (`tree-*`), water (: wading, stepping out, swimming, diving, flowing streams, a waterfall), solid-wall corners and slaloms (), bucket clutches (`clutch-*`), speedbridging (`speedbridge-*`), reflexes (`reflex-*`, knockback off a walkway), MCPK-style gauntlets (`parkour-gauntlet*`), and impossible courses the planner must refuse — most generated by `tools/gen_obstacles.py` (rerun it to regenerate; it never overwrites the hand-curated seeds and `terrain-*`). On enable the plugin copies every bundled fixture missing from `mc-server/plugins/Mai/obstacles/` (never overwriting local edits); run `mai test reload` after dropping files in by hand.
- **Arena world**: `settings.yml` → `obstacle.world` (`name`, `type` = `VOID`/`FLAT`/`NORMAL`, `auto_create`). On enable, an already-loaded world of that name is used as-is; otherwise a dedicated world is created/loaded with the chosen generator (`VoidGenerator` for VOID). Default is a dedicated `obstacles` VOID world. Point `name` at `world` to build in the overworld instead. Horizontal origin is `obstacle.arena_origin` (x/z, default 0/0); floor Y is per-file `origin_y` (default 120). Per-run logs land in `mc-server/plugins/Mai/obstacle-logs/`.
- **Two non-obvious correctness notes** (don't regress these):
  - Pathetic caches chunk snapshots in a **static, never-auto-refreshed** map (`FailingNavigationPointProvider.SNAPSHOTS_MAP`). The harness rewrites the same chunks every run, so `ArenaBuilder` calls `FailingNavigationPointProvider.invalidateChunk(...)` after build/teardown — otherwise pathfinding sees the previous arena and returns `no_path`.
  - The snapshot (and teardown restore) covers the grid plus `SIDE_MARGIN` (8) blocks on every side, so bot edits outside the grid (clutch chains, overshooting bridges) are undone too; in the dedicated void world the margin is also cleared at build. A one-block margin once let a previous run's clutch blocks prop up the next run.
  - `Humanoid.getEntity()` silently respawns a dead body; the harness watches the body it started with (`peekEntity()` + UUID) so a death ends the run as `died` instead of restarting it at the spawn. Before this, deaths at the bottom of a fall were invisible.
  - The arena sits far from spawn; its chunks are pinned with plugin chunk tickets (kept for the plugin lifetime) so the humanoid ticks instead of going invalid (which reads as `died`). The batch waits `SETTLE_TICKS` before each run so a prior run's in-flight async pathfind can't re-cache a stale snapshot.

## Real-terrain courses and human baselines (`me.advait.mai.course`)

Obstacle fixtures are hand-built; courses are boxes of real generated terrain, run by people and by the bot on the same copy, so the bot is measured against a human (the goal is to beat the human's best nearly every time).

- **Files**: `Course` (palette of block-data strings + one index per cell, start position/yaw, finish stand position; gzip, `plugins/Mai/courses/<name>.course`, bundled ones copied from `src/main/resources/courses/` like fixtures; the pom excludes them from resource filtering, which would corrupt gzip), `CourseArena` (pastes into the obstacle world at `course.origin`, writing only cells that differ, plus air over an 8-block margin; `finished` = on the ground, feet over the finish column, at its height), `CourseGenerator`, `CourseManager` (human sessions, bot runs, results), `CourseResults` (`course-runs/<name>/results.csv`: every attempt, `DISCARDED` ones don't count), `CourseLog` (per-attempt tick log in the obstacle log's format, PathDebug events included for bots), `SavedState` (a player's location, mode, health, food, effects; the return point is also in their persistent data so a crash mid-course still sends them back on join), `CourseListener`, `CourseCommand`.
- **Clock**: both runners' clocks start on the first tick they move off the start (a person can look around first; the bot's planning before its first step is free too) and stop on the first tick standing on the finish. The course world has random ticks and fire spread off, so nothing changes between runs. Only one course stands at a time (they share the spot); `course-runs/built.txt` names it so the next start clears it.
- **Menu and finish marker**: `/mai course` (in-game) opens `CourseMenu`, one block item per course (`course.menu.icons`, keyed by course name or its name without the trailing number) with your best, the human best, the bot's best and the gap in the lore; left click plays, right click watches the bot. It is built on `gui/menu/` (`InventoryGUI` + `InventoryButton` lambdas, `GUIManager` routing events by inventory instance); write new menus on that, not the older `InventoryHolder` ones in `gui/`. The finish is a glowing `BlockDisplay` shell around the finish block plus a glowing beam above it (`course.goal`), outlined through terrain, and the action bar shows the distance and an arrow to it. Displays are non-persistent and collide with nothing, so bot times are unchanged.
- **Human runs** (`/mai course play <name>`): adventure mode, full health and hunger (food is locked), effects cleared; the swap-hands key (F) restarts, sneak + F leaves, picking another course or starting a bot run from inside a course switches without quitting first, a fatal hit or falling off ends the attempt and resets after a second, finishing shows the time vs your best and the bot's with a `[Discard]` button (`/mai course discard`), then resets for another try. Per-tick logs record the player's keys from `Player.getCurrentInput()` and actual sprint state.
- **Bot finish**: the bot's walk to the finish has an arrival radius of 0.7 (`FINISH_RADIUS`), so it runs onto the finish block like a person instead of braking to its center (the clock stops on the first tick over the block either way). A radius under 1 requires being within 0.9 of the target's height: with the usual 2.5 the walk ended on a ledge a block above the finish and the run timed out.
- **Bot runs**: `/mai course bot <name> [times]`, `/mai course botall [times]` (in-game you watch as a spectator and are put back after). `[Course] RESULT name=… runner=bot status=FINISHED|FAILED ticks=… reason=… human_best=… beats=<% of human runs it beat>`, `[Course] BATCH`, `/mai course stats` (`[Course] STATS`).
- **Making courses**: `/mai course new <name>` where you stand (facing = start yaw) then `/mai course end [margin]` on the finish block captures the box around both (12 blocks of margin by default). `/mai course generate <name> <biome> [cross|climb|descend|water] [length]` cuts one from a seeded vanilla world (`course.source`, `mai-terrain`, created on first use): it finds the biome (six tries from different origins), scores 24 headings x 3 lengths through it for the mode, and keeps the best start-finish line with dry, standable ends. A generated course isn't checked for reachability: a plateau finish can need blocks (`savanna-1` was, the search exhausted with `state=FAILED`); delete and regenerate those.
- **Hunts** (`/mai course hunt <name> [lead]`, `huntall [lead]`): a Ghost (a player body moved tick by tick along the fastest recorded human run; nothing drives it) is chased by a Hunter with `CombatBehavior` that spawns at the start `lead` ticks (default 40) after the Ghost's first step. `[Course] HUNT name=… status=CAUGHT|ESCAPED ticks=… lead=… gap=<blocks at the end> closest=…`, `[Course] HUNT_BATCH`, per-tick log `<time>-hunt.log` with `gap=` and PathDebug events. This is "the bot hunting the author" without the author. With a 40-tick lead (12-13 blocks) the Ghost escapes on 14 of 15 courses with the gap about where it started: the bot runs at a person's speed, so it holds a gap and doesn't close one in 50 blocks. Where the gap grows, the hunter's path went over `sprint_jump` moves (careful takeoffs) that the course route walks round (jungle: 12 -> 20), or down a cliff (descend).
- **Shipped courses** (15, 48-64 blocks each): forest, birch, dark forest, taiga, jungle, plains, savanna, windswept hills (climb 29), meadow (climb and descend), snowy slopes, badlands, cherry grove, a river crossing and a taiga lake.
- **What they found** (none of it showed on the fixtures): river beds are full of seagrass and kelp, which are passable, so the planner read them as air and walked and sprint-jumped along the bottom until the bot drowned (`MaterialProvider.water` now maps underwater plants and bubble columns to water); nothing made a submerged bot come up for air (`Reflexes.breathe`); diagonal step-ups and step-downs cut across corner cells that were walls (wedged in jungle bushes) or holes (slid off a hillside ledge, replanned the same diagonal forever), now `WalkDiagonal.levelChangeCornersOk`; a step-down never checked the head cell over the landing at the upper level (a leaf canopy); a step-down completed while still on the ledge above the target (`reachedFully` allows 1.5 vertically), so a last step-down ended the walk a block too high.

## Bodies (fake players by default)

- `settings.yml` → `humanoid.body`: `player` (default) or `mannequin`. A player body is a `FakePlayer`: a real `ServerPlayer` with no client, so player physics, hunger, attacks (`Player.attack`), fall damage, drowning and advancements are vanilla's own, and it shows in the tab list and loads chunks like a person. The Mannequin body is the old one, with its gaps from a player patched in `Body`; both go through `Body` and both pass the suite.
- **How a fake player moves**: `ServerPlayer.tick` runs no physics (a client simulates its own player and the server only checks the positions it is sent), so `FakePlayer.tick` calls `doTick()` itself and its connection is never ticked (the connection tick snaps a player back to its tick-start position and would time out keepalives). `isClientAuthoritative()` returns false, which gives server-side ground detection and fall damage. `FakeConnection` is an open `EmbeddedChannel` connection that drops every packet. For a player body `Body` skips the air-assist, swim pull and pose patches (vanilla does them) and adds the client's food > 6 rule for starting a sprint.
- **Build**: the pom depends on `io.papermc.paper:paper-server:26.2.build.133-local`, which is not in any repository: run `tools/install-paper-server.sh` once per machine. The same jar runs on 26.3.
- **Sprint-jump boost**: Paper's `LivingEntity.jumpFromGround` gives a `Player` the 0.2 boost only if 250 ms of wall-clock time passed since its last boosted jump (a real client adds its own boost every jump; the guard stops it stacking the server's copy). `FakePlayer.jumpFromGround` clears `lastJumpTime` first: without it quick repeat jumps (under a two-high ceiling) lost the boost, and whether they did depended on real time, so runs weren't repeatable.
- **Knockback from a player's hit**: `Player.causeExtraKnockback` sends a hit `ServerPlayer` its new velocity in a `ClientboundSetEntityMotionPacket` and then puts the server's copy of its velocity back (a real player's client moves it). `FakeConnection` dropped the packet, so a fake player took no knockback at all from a player or from another fake player. `FakeConnection.send` now hands a motion packet about its own player to `FakePlayer.clientMotion`, which the next tick takes up as a client would.
- **Fresh every spawn**: each body gets a new version-2 UUID (no Mojang account can share it; the harness tells a respawn from the body that died by UUID), is non-persistent (no playerdata), and joins and quits without chat messages (the console still logs `logged in`/`lost connection`). Names are sanitized to 3-16 of `[A-Za-z0-9_]` for the profile; the display and tab names keep the humanoid's name.
- **A fake player is a `Player` to Bukkit**: code that means "a person" must skip `FakePlayers.isFake(p)` (`Assistant.nearestPlayer`/`say`, `Monitor`); `Observation` lists one under `nearby_players` with `"humanoid": true`; `Tools` never resolves a bot's own body as its target.
- **Temporary humanoids** (`Catalog.registerTemporary`): test, chase, duel and course bots are never written to `humanoids.yml`. A server stopped mid-run used to bring them back at the next start, standing on the arena's start block (where a player body shoves the next tester).
- Measured on 26.3 with player bodies: suite 203/203, `chaseall 40` 194/194 with excess 9, `duel 40 basic basic` 22-18, courses 15/15 in 3295 ticks (the author's best runs total 3412; the bot is ahead on 14 of 15, behind only on descend-1, 199 against 144, where the author drops a 17-block cliff for 14 damage and the bot refuses fall damage). Skins are the default; showing one needs a signed texture.

## Checking the physics (`tools/physics_check.py`)

Every obstacle, chase, course and hunt log records per tick the position, the keys actually held, sprint, yaw, ground flag and (`Body.surface`) the slipperiness of the block underfoot and whether the body is in water or on a ladder. Vanilla movement is a closed formula over exactly those, so `python3 tools/physics_check.py <logs>` predicts each tick's displacement from the previous one (drag, key acceleration, sprint-jump boost; gravity and jump vertically) and sorts ticks into `exact`, `slower` (hit something) and `excess` (moved further than the keys allow, or the wrong way). It exits 1 on any excess. Run it after anything that touches `Body`, `FakePlayer` or a controller: last run, 15 course logs 3038 ticks and 203 suite logs 9821 ticks, 0 excess apart from the two `reflex-*` fixtures' scripted `knockback:` shove. The same script over the author's own logs agrees with a real client wherever the server got exactly one client tick per server tick (58% of ticks; the rest are two client moves landing in one server tick). Not covered: water, ladders (skipped), and anything the log doesn't record.

## Movement physics (read before touching jumps or falls)

- **The body only presses keys.** `Body` writes W/A/S/D, jump, sprint and sneak into the Mannequin's own vanilla input fields (`xxa`, `zza`, `jumping`) and turns the view (any float yaw/pitch); the server's `LivingEntity.travel()` does all the physics: acceleration relative to facing, friction, jump impulse and sprint-jump boost, gravity, drag, collisions. **Never call `setVelocity` on a humanoid** (the only exceptions are vanilla game rules applied to it: the sprint-hit 0.6 slowdown in `CombatBehavior`, and `Body`'s own air-assist below). That is what makes the movement vanilla-legitimate by construction, so benchmark results mean something and anticheat has nothing to flag.
- **Mannequin vs player gaps** (copied from the 26.2 source, unchanged in 26.3), all closed inside `Body`: client key input is normalized, x0.98, x0.3 when sneaking, then square-corrected (straight input 0.98, diagonal 1.0; `LocalPlayer.modifyInput`); `speed` is copied from the movement-speed attribute every tick and the attribute's base set to the player's 0.1 at spawn (`Body.prepare`, Mannequin default is 0.7); airborne sprint gets the player's 0.026 air control instead of `LivingEntity`'s 0.02 (the missing 0.006 is added via the `moveRelative` formula); a glancing wall contact (movement within 8 degrees of the key direction, `LocalPlayer.isHorizontalCollisionMinor`) keeps the sprint, where the Mannequin's inherited version called every contact hard and every brush with a corner cost the sprint.
- **Sprint follows the client rules**: starts only with W held (not sneaking, not in shallow water); stops only when W is released, in shallow water, or on a hard horizontal collision. `sprint(false)` while sprinting with W held therefore costs a one-tick W release (a w-tap). Rules are evaluated from the tick-start sprint state plus the final keys, so key order within a tick doesn't matter. `Body.endSprint()` is for game rules that end a sprint (vanilla `Player.attack`).
- **More Mannequin vs player gaps**, also closed in `Body`: while swimming (sprint underwater, which vanilla flags for any entity) `Player.travel` pulls vertical speed toward the view's vertical component (dive by looking down, surface by looking up) and `Player.updatePlayerPose` puts the body in the 0.6-tall swimming pose (kept while crawling with no room to stand); holding shift in water sinks at 0.04 b/t (`LocalPlayer.aiStep` → `goDownInWater`); a swimmer's sprint follows `shouldStopSwimSprinting` (kept at the surface, ends out of water). Paper's entity activation range freezes an entity that stands still away from players; `Body.releaseAll` refreshes `activatedTick` every tick so a humanoid always ticks like a player.
- **The view turns like a head, not a turret** (`Body.View`, `settings.yml -> movement.view`). `look`/`yaw`/`face`/`gaze` turn toward the yaw asked for by `turn_gain` of what is left each tick, at least `min_turn` and at most `max_turn` degrees (`Body.turnStep`), plus a slow seeded wander (`noise_yaw`, `noise_pitch`). Keys pressed with them are relative to the yaw asked for: while the head is still coming round `Body.apply` holds the WASD combination nearest that direction (so a controller that used to brake by turning 180 and holding W now holds S). A turn that doesn't choose a pitch rests it on the ground `gaze_distance` ahead. `aim` is exact and immediate, for clicks that must hit a block face (`Hands`, pillaring, bridging, clutches) and the reflexes. Controllers that predict use `turn` (returns the real yaw; `AirControl`) or `previewTurn` + `aimYaw` (the Runner: every rollout turns its heading with `turnStep`, so `RUN_MISS` stays zero). Measured on the 15 courses against the author's runs: one-tick turns over 90 degrees went from up to 33 a course to none (a person has none), turns over 45 from up to 68 to none, pitch from a constant 0 to 15-37 degrees down (a person: 12-45). `max_turn 180, turn_gain 1`, noise 0 is the old instant view.
- **Keys are released at the start of every tick** (`ServerTickStartEvent`), sneak included; a controller presses what it wants each tick. View direction persists.
- **Internals access**: `Body.init()` resolves the vanilla members via `MethodHandles.publicLookup()` at enable (Paper 26.x runs on unobfuscated Mojang names). A rename in a future version fails loudly at startup. Verified identical members and movement code on 26.2 and 26.3.
- **Model** (vanilla `travel`): displacement this tick = velocity read at tick start + this tick's key acceleration. Then horizontal velocity is multiplied by `air_drag` (0.91) in air, or by `slipperiness * air_drag` (about 0.546) on the ground, including the takeoff tick. Vertical: `vy = (vy - gravity) * vertical_drag`. `Body.groundAccel`/`airAccel`/`accel` expose the exact key accelerations for controllers that predict.
- **`MovementExecutors.walk`** holds W toward the waypoint and angles the view to cancel sideways momentum left over from a turn (what used to be an illegal velocity projection at waypoint transitions).
- **`AirControl.steer`** faces the landing and each tick picks the W/A/S/D combination (of 9) whose predicted touchdown is nearest the landing block's center, braking with S as needed. Used by sprint-jump and both fall types. Don't go back to "push toward the waypoint every tick": it saturates at the drag equilibrium and overshoots every short or tight landing.
- **`AirControl.takeoffSpeeds`** returns the preferred and minimum takeoff speed for a jump. The takeoff speed is not chosen: it is whatever the run-up gave (this tick's ground displacement + the 0.2 sprint-jump boost). The executor jumps early (from the takeoff block) once that speed lands on the center, else at the lip. If the run-up left can't reach the minimum and the bot can still stop on friction before the edge, it backs off with S for a longer run-up. The minimum requires hitbox overlap one tick before touchdown, because vanilla resolves vertical movement before horizontal (the feet drop past the block top before the bot moves forward on the landing tick).
- **Step-ups** jump on the earliest tick whose arc still carries the hitbox over the step by tick 8 (`MovementExecutors.stepUpJumpNow`), from the real speed. There is no speed injection.
- **Takeoff timing**: a sprint-jump takes off on the last tick the hitbox still overlaps the takeoff block, when this tick's move would carry the center more than `TAKEOFF_EDGE_LEAD` (0.25) past the lip, like a player at the edge. **Planner run-up check**: `SprintJump.runUpSuffices` simulates sprint acceleration from a standstill over the run-up the terrain offers (straight behind the jump, or a compass line within 50° of it, counting only its component along the jump) with the same trigger (`predictTakeoff`), and rejects jumps that speed can't make. Keep planner and executor in sync.
- **Sprint-jump cost** = `walk_flat * distance + sprint_jump_base + gap * sprint_jump_per_gap + ...`. It must never be cheaper per block than walking, or A* plans the longest jump that fits, including "jumps" over flat ground.
- `SprintJump.matches` also requires a real gap (some column under the line has no floor at the source level) and a dry, solid, non-slow takeoff.
- `FallSafe`/`FallUnsafe` check the **landing** column from source height down (plus the corner columns for diagonal drops). Standing on the landing is success regardless of phase.
- The driver chains into the next waypoint in the same tick when one completes, so no tick goes without a decision. Key presses are idempotent within a tick, so chaining never double-accelerates.
- Arrival requires being on the ground; passing over the target column mid-jump is not arriving.
- **Corners and any-angle walking** (measured on the `wall-*` courses: slalom 105 -> 58 ticks, 1-wide corridor 205 -> 77, no wall contacts). Planner paths are 8-way grid steps; the driver drops a level-walk waypoint whenever the hitbox has a straight clear line to the one after it (`skipStraightWaypoints`, `WAYPOINT_SKIP`; `MovementExecutors.hitboxLineClear` sweeps the hitbox plus a clearance from feet to head and needs level floor under the center), so the bot runs straight across open ground like a player. A level walk completes only once the hitbox has a clear line to the next waypoint (`walkArrived`): completing at the 0.5 radius and turning cut every inside corner into the wall. When the waypoint isn't in hitbox line of sight (drifted or knocked off the line) `walk` aims at the furthest visible point of the segment instead, without sprint or emergency jumps. The drift canceller stands down while touching a wall (it pinned the bot to the wall it should slide along), and a flat run-jump needs its speed along the jump and the full hitbox clear (right after a turn it threw the bot into the corner it had just rounded). An exact-block arrival sprints until 1.2 from the target (friction stops a sprint within ~0.34).
- **Running** (`navigation.sprint_jump_flat`, `pathetic/movement/Runner` + `RunSim`, `driveRunner` in the driver): on plain ground moves (walk, diagonal, step up/down, safe falls) the driver does not visit waypoints. Every tick `Runner.plan` plays candidates forward in `RunSim` (one tick of vanilla player land physics against real collision shapes: sprint rules, jump and boost, step-up, fall distance) for 28 ticks: aim 1.5/2.5/4/6 blocks ahead on the route x first jump after 0/1/2/3/5 ground ticks or never x jump again on every landing or not, always W + sprint. A candidate that takes fall damage, touches what the sim doesn't model (liquids, climbables, hazards, soul sand/honey/slime), stands more than 1.25 off the route or 0.6 off its height, or overshoots the end is thrown out; the one furthest along the route wins and its first tick's keys are pressed. The route is the planner's path from the body's position (rebuilt whenever it stands), so the pathfinder still decides where to go. When nothing is valid `plan` returns null and the movement's own executor has the tick (`RUN_NO <reason>` in debug mode; `route_end` before a non-run move is normal). `pickUpWaypoint` moves the path index to the segment the body stands on (`RUN_AT`). While the body is where the sim put it (`runnerOnPlan`, 0.2) time in the air is planned and the reflexes leave it alone. Rules found the hard way: the sim must match the server exactly, and `RUN_MISS` (prediction vs actual, debug mode) is the signal: it is zero on all 15 courses, keep it there (a player's leftover horizontal speed is zeroed below 0.003 combined, not per axis; ground acceleration is `speed * 0.98 * 0.98`); when every straight candidate runs into something, headings turned 25/50 degrees for 5 ticks are tried too (a hitbox overlapping a block corner by 0.3 pushed into it forever); a plan whose first step neither moves the body nor jumps is not a plan, and a jump now is taken over a later one within 0.3 (re-planned every tick, "wait one tick then jump" was chosen forever: 76 ticks against a ledge); a plan that gets under 0.5 in 28 ticks hands the tick back (`no_progress`), so the driver's stuck handling still works. a plan must end where the body can still stop on the route by letting go of the keys (`canStop`), and the runner stands down on anything slipperier than 0.6 (`slippery`: every candidate holds W + sprint, and it jumped along an ice walkway and slid off the corner); standing on a block's edge with the center over air, friction is the supporting block's (`RunSim.frictionUnder`, vanilla `getOnPos`), not the air cell's. Every candidate sprints, so on a cliff too tall to drop safely nothing is valid and the old `fall_safe` executor climbs down ledge by ledge (descend-1, the end of savanna-2): walking or braking candidates are the next step there. `RUN_STALLED` (debug mode) lists every candidate's score or rejection for a body that isn't moving. Planning costs 0.2-2 ms per tick (`us=` on `RUN_JUMP`). `StepDown` steers the last drop of a walk onto the block's center with `AirControl`. Of the candidates within 0.15 of the best, the one that turns the head most like it was already turning is taken (`SMOOTH_SLACK`): on the top score alone the aim point changed every tick and the head twitched left and right. Chasing (an arrival radius), the route goes on past the path's end to where the target is now (`CHASE_EXTEND`): with the stale end as the end of the route, every jump that carried past it was thrown out.
- Pathfinding takes about 50-100 ms per request on this server. The search itself is fast; the time is Pathetic's async handoff plus one main-thread tick for annotation.

## Parkour (any direction)

- `HumanoidNeighborStrategy` offers every landing within `SprintJump.maxReach(dy)` (3.61 up one, 4.5 level, 4.7 down one, 5.0 down two or three) in **any** direction, not just the four axes: 2+1, 3+2, diagonals, scattered blocks, trees. It used to be cardinal-only, which is why the bot couldn't parkour to blocks placed at an angle.
- `SprintJump.validateArc` sweeps the 0.6-wide hitbox along the straight line from source to landing center, checking feet-to-head at the heights the arc passes (source level for the first half, one higher near the end of an ascent, down to the landing level near the end of a descent).
- Measured limits (all from real runs): a 3-block gap from a lone 1x1 pillar is possible (`pj-3g-standing`); 4 from a lone pillar is not (`impossible-pj-4g-standing`).
- Cost: bridging searches got slower with ~900 offsets per node (0.5-0.8 s for a 30-block void bridge; parkour/terrain searches stay 20-150 ms). Falls go down to `LONG_DROP` (64) for water landings and clutches; each fall type enforces its own limit.

## Water

- `Swim` is one cell at a time (it used to match any offset ending in water, so jumps or 5-block "swims" were planned) and costs 1.5x with the head under water. The executor surface-swims (W + hold jump) on the last stretch and **sprint-swims** on open water: shift to duck under (a sprint can't start with the head above water), then sprint with the view steering depth, coming up when air runs low.
- In water `MovementExecutors.walk` holds jump unless heading down: pushing into a bank while rising triggers vanilla's 0.3 b/t climb-out boost, which is how it steps out of shallow water. On a film under 0.4 deep that is a full ground jump: hopping up a stream is far faster than wading against its drag and current (wading upstream is 0.026 b/t in vanilla; `water-river-upstream` 246 -> 148 ticks). `SprintJump` never takes off from water.
- Two deep means water over the feet's block (standing on the bed) or under it (floating at the surface). Only the first was tested, so a bot floating across a river never ducked under and paddled at 0.096 b/t instead of 0.19 (river-1 405 -> 284 ticks).
- The planner prices water two deep at `costs.swim_sprint` (5.26 ticks a block, 3.8 b/s) and the rest at `costs.swim` (9.09). With one paddling price a river was something to get out of: on river-1 the route left the direct line for a narrow crossing and ran round on land. Searches through open water take 2-3 s there.
- **Getting in**: where a run of ground moves is followed by `swim` or `fall_into_water`, the Runner's route goes on over the swim waypoints (`Route.waterFrom`) and a candidate that goes into the water there has arrived, the sooner the better, so the bot sprints and jumps off the bank like a player and goes under on its own momentum (`RUN_SWIM` picks up the swim waypoint it landed at). Before, the step-down and careful-drop executors walked it to the edge and it sank with shift: 22 ticks lost on river-1 (290 -> 258). Standing (on the bed, or on the bank's lip with deep water ahead) `Swim` walks: shift there is sneaking, which won't step off an edge.
- `Swim` sprint-swims only where the water is two deep: holding shift to duck under never gets the head wet in a shallow stream, so the bot crept at sneak speed until the current beat it (the reported "didn't follow me into the stream"). Shallow water is waded. `Reflexes` treat water below as a safe landing (it was read as void, so every hop over a stream was "rescued" back toward the bank). Flowing-water courses: `water-river-upstream`, `water-river-current`, `water-waterfall-up`.
- `FallIntoWater`: drops of any height into water (vanilla resets fall distance on water contact; even a one-deep puddle).
- Measured limit: a bank a full block above the water surface can't be climbed from deep water (the boost peaks ~0.1 short), so the planner never swims into such a pool (`impossible-water-ledge`).

## Hands (vanilla-strict right click)

`Hands.placeBlock(entity, against, face)`, `emptyBucket`, `fillBucket` are the only way a humanoid places blocks or uses a bucket. Each turns the view onto the exact face point and requires a ray from the eyes along the view to hit that block and face first (`canSee`, 4.5 reach), a replaceable target cell that no hitbox overlaps (vanilla won't place into an entity, the bot's own body included), and the 4-tick right-click delay. Before this, placement only checked for a solid neighbour: the old bridging placed against a face behind the bot's eyes, and pillaring placed into its own hitbox.

## Speedbridging and pillaring

- `BridgePlace` speedbridges like a player: face back along the bridge, look down (~78°), walk backwards with S; once the center hangs 0.02-0.29 past the edge, the block underfoot's side face is in view below the heels, so click it and keep backing. Each tick it predicts its displacement and holds S, nothing, or W (brake) so the center never passes the point where the hitbox loses the block. Measured: one block every ~4.6 ticks at backward walk speed (~4.2 b/s), placements landing 0.03-0.22 past the edge. Strafe keys hold the centerline.
- `place_block_cost` is now 2.0 (was 20): bridging really costs ~1.3x walking, and the inflated price made A* explore huge void cones.
- `PillarUp` looks straight down and places only once the feet clear the cell (vanilla refuses to place into the bot's own hitbox), after letting leftover momentum die on friction.

## Clutching

- **Planned water clutch** (`WaterClutch`, with a water bucket, drops of 6+): walk (or jump) off, steer over the landing, look straight down and empty the bucket on the landing block's top face, then scoop it back up after the 4-tick delay. Vanilla only spares the fall if the water is there before the landing tick's move (`LivingEntity.checkFallDamage` rechecks water after the move), and the click must reach the face (feet at most ~2.8 above it). Falling 2-4 blocks a tick, that window can fall between ticks, and tick positions are fixed by the drop height, so `placementTick` simulates the fall and the bot walks off or jumps off, whichever has a tick in reach; the planner only offers clutches that have one. Measured: 25 and 40-block drops, placed with the feet 1.6-2.2 above the block, full health.
- **Reflexes** (`Reflexes`, every tick before the controllers, only for falls no planned movement expects): a hurting fall over ground with a bucket → water clutch the same way (and scoop the puddle back up); a lethal or bottomless fall with blocks → **chain clutch**: predict where the fall crosses the level it left (vanilla no-input air physics) and build out along that level toward it, one block per click, starting while still rising after a knockback; else a block under the hitbox against any visible side. While a reflex drives, it air-steers back toward the last ground and the walk controller stands down; afterwards the walk replans (`takeRescued`) instead of following the old path back over the void. Measured: knocked off a 1-wide walkway over void by a 0.45 hit, a 2-3 block chain catches it; knocked off a walkway 24 up, it water-clutches, scoops the water and pillars back up, full health.

## Real terrain (partial and special blocks)

The planner only sees `Material`s, so the executor reads real collision shapes where it matters. Don't regress these:
- `PatheticAgent.feetCell` maps an entity standing on a partial block (slab, dirt path, farmland, soul sand, carpet, chest) to the cell above it. Without it, start and target cells sit inside the floor block and every walk to a player on a path block fails.
- `MovementExecutors.collisionTop` uses the block's collision shape, not `getBoundingBox()` (a fence's outline is 1.0, its collision 1.5). `stepRise`/`needsJumpUp` skip the jump for rises within the vanilla 0.6 step height (slabs, paths, carpet), and StepUp completes when the feet are on the real top. `obstacleAheadNeedsJump` only hops rises in (0.6, 1.25].
- `BlockClassifier`: lava, fire, soul fire and wither roses are never traversable; `Swim` is water-only. Fences, walls and gates are `isTall` (1.5): never a floor, so never a step. Wooden doors and fence gates are `isOpenable`: passable to the planner, and the driver opens them (`openDoorsAhead`). Iron doors stay solid.
- `SprintJump` never takes off from a slow block (soul sand, honey): the takeoff model assumes full sprint speed.
- `slipperinessBelow` samples 0.5 below the feet like vanilla, so it reads a slab or path itself rather than the block under it.
- Terrain fixtures are `terrain-*` (slabs, paths, carpet, soul sand, ice, fences, gates, doors, iron door, stairs, a mixed village street).

## Assistant (commands, chat, and the future LLM interface)

- **One entry point.** Every capability is a named tool in `assistant.Tools` with typed params (`status, come, goto, follow, guard, attack, stop, mine, place, look_at, jump, say, inventory, equip, give, teleport_to`). `/h` commands, chat and `/mai do` all call `Tools.run(name, humanoid, jsonArgs, requester)`, which returns a `CompletableFuture<String>` (immediate for behaviors, on completion for queued work; failures are `ToolException` messages for the user). `Tools.schema()` renders JSON-schema function definitions and `Observation.of(h)` the matching state, so an LLM loop is: observe, pick a tool, run it. Add new abilities as tools, not as bespoke commands.
- **One job at a time.** `Assistant.of(h)` holds either a `Behavior` (ticked every tick by a shared ticker) or the action queue; `setBehavior`/`run`/`stopAll` cancel the other. Don't drive actions or behaviors around it.
- **Moving targets.** `HumanoidWalkToRunnable` has an `arrivalRadius` and `retarget(Location)`; a retarget replans only when the current movement is safe to cancel. Chase rules (each found with the chase benchmark): replans are requested and adopted only with footing (ground, water, ladder), never mid-jump (a path planned at a run-jump's apex starts in the air and stuck on a "step down"); a new path waits as `pendingPath` until the movement is safe to cancel, then is spliced at the bot's position instead of index 1 (`adoptPath`; never past a pillar/bridge/mine/clutch step); when it continues with the same movement to the same cell, that movement keeps its state (run-up and takeoff timing); with an arrival radius the bot sprints in instead of slowing near the target, and it keeps sprinting round corners unless the ground straight past the corner is missing. `GroundTracker` resolves a target mid-jump over a gap to where it last stood (pathing at the air cell is refused, and each refusal cost a second), and a target well above the ground under it (1.75+, jumping between pillars) to the nearest block beside it rather than that ground (the hunter ran along the floor under `pk-scatter-up`, 64 ticks late, about one run in six). `Navigator` wraps this for behaviors (one live walk, retarget only after the goal moves 2+ blocks, 1 s back-off after a failure). `FollowBehavior.landingSpot` resolves a jumping/flying target to the standable cell below it, or to the water it swims or falls into (water is a path endpoint; before, a swimming target resolved to the bank it left). Combat paths whenever either side is in water (direct steering sank), and `Motor.drive` holds jump in water.
- **Combat** (`CombatBehavior`, vanilla rules only): pathfind when far, out of sight, more than 1.5 blocks up or down, or when the straight line isn't plain walking (`Motor.walkableLine`: a gap, a rise over 0.6, a drop over 1); else step directly with `Motor`. Up close it moves the best weapon into the main hand (pathing leaves blocks or a pickaxe there, and those swing at fist speed), and a main-hand change resets the attack charge like vanilla `Player.tick`. Direct stepping uses the same `Body` keys as the path executor. Swings only within 3.0 reach (eyes to hitbox) at the weapon's attack-speed cooldown with vanilla charge scaling (`0.2 + 0.8c²`); crits by jumping and swinging while falling without sprint (x1.5); sprint hits add the vanilla extra knockback, slow the attacker and end its sprint (`Body.endSprint`), then hold off sprint 2 ticks (w-tap); strafes and never steps off a ledge. `ItemUtil` reads the effective attribute-modifier component (item defaults included). Style `BASIC` is the naive baseline for duels.
- **Duel benchmark** (`mai duel`): two humanoids on a platform at x=400 in the obstacle world; prints `[Duel] RESULT`/`SERIES`. It is only fair because sides swap every round, spawn order alternates every two rounds (the server ticks entities in spawn order, and moving first means swinging first: basic-vs-basic was 15-5 before), and the assistant ticker shuffles behavior order each tick. Check `mai duel 40 basic basic` stays near 20-20 after touching it. Findings so far (40 rounds each vs BASIC, iron sword): w-tap 23-17, recharge-only crits 21-19, both 23-17 (noise-level); strafing 17-23 (no aim to dodge, slower approach); approach crits 0-40 (airborne you're hit first and knocked further); `space_out` (back out of reach while recharging) 19-21. Why everything is noise vs BASIC: per-round stats show both sides land 3-4 full-charge sprint hits (6 each), sprint knockback separates them after every hit so neither ever recharges inside reach (no crits happen), and each re-entry is a symmetric full-charge trade won by whoever acts first that tick. Beating a perfect-aim rusher on flat ground needs a real reach or timing asymmetry, not footwork tweaks. Hence the defaults: crits on (recharge hops only), `approach_crits` and `strafe` off. Reach is symmetric on the ground, so full-charge trades are coin flips; an airborne fighter's eyes are above the target, which lengthens its own reach to the target.
- **Chat**: "<Name>, follow me", "@Mai mine this", "mai attack nearest". `ChatIntents` is keyword rules returning (tool, args). Permission `mai.humanoid.command` (op by default).
- **Claude chat brain** (`LlmBrain`, off by default): with `assistant.llm.enabled: true` and a key (`assistant.llm.api_key` or `ANTHROPIC_API_KEY`), chat goes to Claude (official `anthropic-java` SDK, loaded by Paper from plugin.yml `libraries:`, so it is `provided` in the pom). Each message is a fresh request: system prompt + the last 8 chat lines + `Observation` JSON + the message, with every tool except `say` (plain text is spoken). Tool calls run on the server thread; one-shot jobs are awaited up to `tool_wait_seconds`, then reported as still running. Any API failure falls back to `ChatIntents`. Console: `mai ask <humanoid> <message>`.
- Tunables live in `settings.yml -> assistant:` (follow distance/teleport distance, combat reach/range/crits/strafe/w_tap/min_charge, guard radius), read live.

## Tuning (for humans now, models later)

`MovementTuning` exposes every leaf under `movement:` as a key such as `costs.walk_flat` or `navigation.stuck_replan_ticks`. `snapshot()`, `get`, and `set` validate the key and type, then rebuild `MovementConfig` and the registry immediately. `applyProfile(name)` applies `movement_profiles.<name>` (shipped: `default`, `safe`, `speedrun`; write profiles as nested YAML, not dotted keys). `save()` persists. In-flight walks keep their config; new walks use the new one. The driver's replan and stuck thresholds are config too (`navigation.lookahead_depth`, `periodic_replan_ticks`, `emergency_jump_ticks`, `stuck_replan_ticks`). Console: `mai tune ...`.

## Block editing in the pathfinder (mining & placing)

The pathfinder treats the world as **mutable**: it will break or place blocks as part of an A* route, and re-paths when the world changes. Do not "fix" this by stripping the editing moves — it's intentional.

- **Moves**: `MineThrough`/`MineStepUp` break the breakable block(s) in the way then walk/step in; `BridgePlace` speedbridges a support under the next cell across a gap; `PillarUp` jumps and places a block under the feet (see "Speedbridging and pillaring"). Each `matches()` only fires on cells the natural moves reject (blocked-but-breakable, or floorless gap), so they never shadow free locomotion.
- **Execution reuses existing actuators**: mining drives `MannequinBlockBreaker` (multi-tick; the in-flight future lives on `TickContext.subAction`, reset by the driver on every waypoint advance/replan); placing goes through `Hands.placeBlock` (vanilla-strict, see "Hands"), the `/h place` tool included (`HumanoidBuildAction.placeBlock` tries each solid neighbour face the eyes can see).
- **Mining/placing visuals**: both call `entity.swingMainHand()`; mining additionally broadcasts the vanilla block-cracking overlay each tick via `Player.sendBlockDamage(loc, progress, mannequin)` to players within 64 blocks, throttled to destroy-stage changes and cleared (progress 0) on cancel — a successful break clears it client-side on its own. Caveat: the swing animation may not render on a `Mannequin` (it is a display-oriented entity; `swingMainHand` already reaches the NMS swing broadcast with no `Mob` guard, so non-rendering is a client-side limitation, not something the server can fix). The crack overlay renders regardless since it is attached to the block. No-op when no players are nearby (e.g. the headless obstacle world).
- **Cost model** (all in ticks, summed with the existing costs): mining = `hardness * divisor / toolSpeed + durabilityPenalty` (`divisor` 30 with the right tool / 100 without); placing = `place_block_cost + equip_cost + value_weight * placementValue(block) / log2(count+2)`. Scarcity means the bot bridges with cobblestone (value 1, abundant), never a diamond block (value 4000) unless that's all it has. Unbreakable/protected blocks and "no block to place" cost `cost_inf` (never chosen). Constants live in `settings.yml` → `movement.{mine,place}` and `movement.pathfinding.{mining_enabled,bridge_enabled}`; `HumanoidCapabilities.from()` pre-extracts thread-safe tool/placement numbers on the main thread for the async cost processor.
- **Adaptivity**: `BlockClassifier` gained `isBreakable`/`hardness`/`placementValue`. `WorldChangeListener` (block break/place/burn/fade/decay/explode events) invalidates the pathfinder's static snapshot cache (`FailingNavigationPointProvider.invalidateChunk`) and flags nearby in-flight `HumanoidWalkToRunnable`s (`onWorldChange` → `worldDirty`) to replan immediately. The bot's own edits bypass Bukkit events, so `MannequinBlockBreaker` and `HumanoidBuildAction.placeBlock` invalidate the snapshot directly. `worldDirty` is a 4th replan trigger in the runnable alongside pathNull/lookahead/periodic.

## Conventions

- **Commit messages**: short single-sentence subject only, no body, no Claude footer. See [[feedback_commit_style]].
- **Pathfinding correctness**: when in doubt, surface a `PathDebugLog.event(...)` line. The debug log is the user's primary way to diagnose stuck bots.
- **Never snap the target to the ground** — long-term the bot needs to bridge to elevated targets. Resolve block-coord ambiguity (e.g. edge-standing players) by checking AABB corners, not by moving the target.
- **Physics constants** live in `settings.yml` → loaded into `MovementConfig`. Don't sprinkle magic numbers into movement types.
- **Console-safe APIs**: anything the harness or future CI needs must take `CommandSender`, not `Player`. Use `Bukkit.getWorlds().getFirst()` (or a configured arena world) when no player context exists.
